# External runtime performance research

2026-11-17. Source comparison for the Android Vulkan port and the Galaxy S23+ (8 GB, Adreno 740).

## What the phone establishes

Build 10017 uses 32 MiB image blocks, an 8 MiB staging retention target per slot, and compact descriptors in low-memory mode. Its main process was killed by Android for foreground `LOW_MEMORY` after 831 seconds, on the warp from the surface into Iu'iqoi lightroot. A fresh process reached the same lightroot, sprinted in the Depths, and warped back. The test changed process age, the prior route, and cache state together. The 1.21 GiB figure near the long run's end was system-wide KGSL shared usage. Earlier data showed about 129 MiB unused inside 640 MiB of allocated image blocks, without revealing how much could be released or belonged to a dispensable cache. During the 10017 warp, the used bytes in image blocks rose from 371 to 572 MiB between samples, committed blocks grew from 640 to 704 MiB, and dedicated images held at 79 MiB. The final sample showed 480 MiB in use across those 704 MiB of blocks. That difference is allocator slack within blocks and cannot be counted as immediately reclaimable memory. [Device evidence](s23-device-validation.md#sustained-streaming-in-akkala)

At a sampled 120 Hz, an earlier 7.8 FPS window created no pipelines while memory stalls rose. On a separate surface segment, build 10017 spent 776.5 ms on two synchronous pipeline creates in a window with a 900 ms maximum frame. Measure memory-driven slowdown and first-use pipeline hitches separately. [Device evidence](s23-device-validation.md#sustained-streaming-in-akkala), [Android LMKD and PSI](https://source.android.com/docs/core/perf/lmkd)

## The most applicable source findings

- **totk-pc-recomp · Vulkan on Windows/Linux, MIT.** This is the closest reference for the same game and API. It budgets released textures by bytes and device memory pressure. The sweep prefers released textures whose storage has since been reused, then clean mirrors that can be uploaded again. It waits for inactive finalized slots and tracks dropped entries that come back soon. Its source records black flashes in a Depths fight after eviction based on age alone, and a desktop run where gradual trimming reduced memory without increasing the slow frames. The sizes and storage-reuse rules belong to its allocator and cannot be assumed on Android. On UMA it also constrains its effective Vulkan budget by system memory headroom. [Texture reclamation](https://github.com/valentderah/totk-pc-recomp/blob/6151ac4fbc2c490207116609fbf4974b01843763/runtime/vk_texture.c#L604-L833), [Host memory headroom](https://github.com/valentderah/totk-pc-recomp/blob/6151ac4fbc2c490207116609fbf4974b01843763/runtime/vk_memory.c#L628-L707), [License](https://github.com/valentderah/totk-pc-recomp/blob/6151ac4fbc2c490207116609fbf4974b01843763/LICENSE)
- **Eden · yuzu-family emulator, GPL-3.0.** The pinned texture GC uses increasingly aggressive age and work thresholds. Evicting a dirty texture that needs to be downloaded can finish the GPU queue and swizzle data back into guest memory on the CPU. An open draft proposes a resumable sweep, which gives a model for bounding scan work. The synchronous download is a source of extra work during exactly the transition under study. Eden's optional async pipeline path also waits for draws with GPU side effects and some offscreen draws, a useful illustration of dependencies that extend beyond the current frame. [Texture GC](https://git.eden-emu.dev/eden-emu/eden/src/commit/d85bad89248fcae68f812d7e1c937436261404cb/src/video_core/texture_cache/texture_cache.h#L117-L182), [Draft sweep PR](https://git.eden-emu.dev/eden-emu/eden/pulls/4684), [Pipeline readiness rules](https://git.eden-emu.dev/eden-emu/eden/src/commit/d85bad89248fcae68f812d7e1c937436261404cb/src/video_core/renderer_vulkan/vk_pipeline_cache.cpp#L787-L822), [License](https://git.eden-emu.dev/eden-emu/eden/src/commit/d85bad89248fcae68f812d7e1c937436261404cb/LICENSE.txt)
- **Ryujinx · emulator, MIT.** Its texture LRU uses both count and byte limits. The cache synchronizes dependencies and flushes modified data in the relevant eviction path before dropping its reference. Its separate renderer command queue and shader disk cache are precedents for features this fork already has in another form. The original source is cited via a source archive. [Texture cache](https://git.axenov.dev/Museum/ryujinx/src/commit/fec4f4ada9f28f897457033f9954c84cc15d0b02/src/Ryujinx.Graphics.Gpu/Image/AutoDeleteCache.cs#L49-L170), [Command queue](https://git.axenov.dev/Museum/ryujinx/src/commit/fec4f4ada9f28f897457033f9954c84cc15d0b02/src/Ryujinx.Graphics.GAL/Multithreading/ThreadedRenderer.cs#L20-L155), [Shader cache](https://git.axenov.dev/Museum/ryujinx/src/commit/fec4f4ada9f28f897457033f9954c84cc15d0b02/src/Ryujinx.Graphics.Gpu/Shader/ShaderCache.cs#L58-L110), [License](https://git.axenov.dev/Museum/ryujinx/src/commit/fec4f4ada9f28f897457033f9954c84cc15d0b02/LICENSE.txt)
- **nxnative and MacNativeGames · native ARM64 and Metal, MIT.** MacNativeGames has a direct TotK port and documents first-visit compile stutter. nxnative recycles heaps after GPU completion and trims by age and capacity. Its separate scratch-arena policy keeps frequently reused blocks and releases completed peak allocations after an idle interval. The closest analogues here are existing image suballocation and staging retention. The useful detail is a best-fit reuse policy that leaves oversized transient blocks idle long enough to release. [MacNativeGames TotK status](https://github.com/ly05010419/MacNativeGames/blob/20753d3628cd63963ca63b2f1a401b13783cae74/README.md#L42-L50), [MacNativeGames first visits](https://github.com/ly05010419/MacNativeGames/blob/20753d3628cd63963ca63b2f1a401b13783cae74/README.md#L127-L135), [nxnative texture heaps](https://github.com/seedds/nxnative/blob/e4b0d9b75d39c41c10fdcfec2f0b070df496d7e5/dm/gfx/nvn/nvn_mtl.m#L416-L485), [Scratch arenas](https://github.com/seedds/nxnative/blob/e4b0d9b75d39c41c10fdcfec2f0b070df496d7e5/dm/gfx/nvn/nvn_mtl.m#L7793-L7838), [MacNativeGames license](https://github.com/ly05010419/MacNativeGames/blob/20753d3628cd63963ca63b2f1a401b13783cae74/LICENSE), [nxnative license](https://github.com/seedds/nxnative/blob/e4b0d9b75d39c41c10fdcfec2f0b070df496d7e5/LICENSE)
- **nx2android · native ARM64 and Vulkan, MIT runtime.** Its published TotK 1.4.3 status makes open-world performance an ongoing target. It separates portable shader assets from a validated, driver-specific, atomic disk cache and writes after a burst of new pipelines, subject to size-dependent throttling. Android already has a comparable coalesced saver and separate portable seed, plus two recorder workers by default. nx2android's copied-pool snapshots address GPU/CPU byte merging but add one byte of CPU memory for each byte in a copied pool. First verify the sizes and paths that actually use copies on the S23+ before considering any such change. [Game status and replay option](https://github.com/shirai91/nx2android/blob/f3da64f7816209491e66e902af52b00fd39ca4c8/README.md#L39-L71), [Disk cache and snapshot design](https://github.com/shirai91/nx2android/blob/f3da64f7816209491e66e902af52b00fd39ca4c8/docs/ARCHITECTURE.md#L54-L100), [Cache saver](https://github.com/shirai91/nx2android/blob/f3da64f7816209491e66e902af52b00fd39ca4c8/nxnative/dm/android/gfx_vk_pipeline_cache.inc#L29-L54), [Runtime license](https://github.com/shirai91/nx2android/blob/f3da64f7816209491e66e902af52b00fd39ca4c8/nxnative/LICENSE)
- **UltraTears · native TotK 1.4.3 for PC and Steam Deck, GPL-3.0.** It moved some image block allocations off the render path after measuring an image creation burst during asset streaming. That reserves an extra block and is disabled there under VRAM pressure. Its parallel Vulkan recorder also avoids full barriers between chunks whose only relationship is their order, and retains barriers for uploads, interrupted passes and writes. Its source records a shadow regression from splitting depth-only passes. Both ideas are useful when diagnosing frame traces. Speculative allocations are a poor first experiment on the 8 GB device. [Allocator](https://github.com/kuraeow/ultratears/blob/cb6e7421b7e5ba44c8091b2f1a401b13783cae74/src/gfx/vkb_tex.c#L502-L550), [Chunk barriers](https://github.com/kuraeow/ultratears/blob/cb6e7421b7e5ba44c8091b2f1a401b13783cae74/src/gfx/backend_vk.c#L3248-L3267), [License](https://github.com/kuraeow/ultratears/blob/cb6e7421b7e5ba44c8091b2f1a401b13783cae74/LICENSE)

These are source observations and experiment designs. Performance figures from other platforms are project-reported. The other runtimes were not benchmarked on the same S23+ route. This research imported zero source files. GPL projects were used as design references. Any later MIT adaptation needs file-level provenance and the original notices. ## Experiments in order

1. **Find which memory can actually be reclaimed before an aged warp.** Add byte and age buckets for unreferenced shared images, retired images waiting for fences, and active images, splitting GPU-authoritative content from proven recoverable content. Include native-size and AA/feedback siblings, image block live bytes, largest free span, staging, and CPU-side memory. Track each bucket across the same surface sprint and surface-to-Depths warp. The current `vk_res_sweep` retains unreferenced shared images for 600 submissions and already protects pending writebacks. CPU mirrors outside this shared cache already retire on release, so a byte budget alone may find few safe candidates. If there is a sizable eligible population, prototype a bounded, resumable trim at submission boundaries in low-memory mode. Count allocations actually freed after their fences, peak combined pressure, recreations and reuploads after a trim, and p95/p99 frame times. Use a conservative Android memory signal alongside the extension where available, since its heap budget is implementation-dependent. Require proof of current backing ownership or content recoverability, no in-flight bind or pending writeback, and correct alias recovery. Leave GPU-only contents of uncertain ownership intact. Check for flashes, stale textures and missing effects in a repeat Depths fight and on return to the surface. [Fork image retirement and accounting](../games/totk/android/gfx/vk_res.c), [Khronos memory budget](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_memory_budget.html)
2. **Warm the expensive pipeline keys observed in actual routes.** The fork already persists driver binaries with context validation, saves prewarm key progress, and prewarms graphics on a low-priority worker outside low-memory mode. Check first whether the 776.5 ms was a pair of cache misses, shader preparation, or another stage of creation. Record full pipeline key, shader load and translation time, Vulkan create duration, and valid app-cache-hit feedback when supported. Then test a small set of repeatably expensive keys during a natural load window, with the existing worker, a memory/time cap, and demand work prioritized. Compare identical cold and warm driver runs and capture PSO counts, peak memory, load duration and p99/maximum gameplay frames. Preserve synchronous readiness for persistent captures and resource-producing work. A driver binary cache is specific to the Vulkan device/driver context. Saving finished stage libraries or large archives in memory also has a cost. The PC port defaults to keeping zero extra prebuilt stage libraries, and nxnative reports background prebuild contention on iPhone and substantial archive footprint in one Breath of the Wild case. [Current cache and prewarm](../games/totk/android/APP.md#shader-compiles-and-the-pipeline-cache), [S23 low-memory defaults](../games/totk/runtime/android_memory.h), [Vulkan cache header](https://docs.vulkan.org/refpages/latest/refpages/source/VkPipelineCacheHeaderVersionOne.html), [Vulkan cache feedback](https://docs.vulkan.org/refpages/latest/refpages/source/VkPipelineCreationFeedbackFlagBits.html), [PC pipeline prebuild](https://github.com/valentderah/totk-pc-recomp/blob/6151ac4fbc2c490207116609fbf4974b01843763/runtime/vk_pipeline.c#L2642-L2661), [nxnative prebuild costs](https://github.com/seedds/nxnative/blob/e4b0d9b75d39c41c10fdcfec2f0b070df496d7e5/docs/development.md#L819-L823)
3. **Profile the pipeline-free hitches with recorder and GPU timing.** Record command-walk thread CPU versus wall time, fence and readback waits, slow image allocation/upload calls, queue wait, longest recorder job, GPU time and system pressure in the same frame windows. The reported 49.947 ms walker wall and 20.640 ms thread CPU suggest time outside the walker's own CPU work. Other threads, GPU waits and OS descheduling are distinct hypotheses. The PC port and UltraTears suggest looking for long chunks occupying one worker or barriers inserted at chunk boundaries. First compare the fork's existing recorder controls on the same warm-cache route. Changing how commands are partitioned requires checking inline uniform snapshots, alias and texture writeback order, and shadow-pass output. Previous Thor runs rejected uniform interning, broader persistent binding work and nxnative deswizzle/hash changes after device comparisons. Repeating them or adding more workers before measuring contention would obscure the cause. [Fork recorder and pool maintenance](../games/totk/android/gfx/vk_record.c), [Android recorder options](../games/totk/android/APP.md#frame-rate), [Prior on-device experiments](translation-research.md), [PC parallel replay hazards](https://github.com/valentderah/totk-pc-recomp/blob/6151ac4fbc2c490207116609fbf4974b01843763/docs/architecture.md#L86-L100)

Eden also queues GPU deswizzling for sufficiently large, eligible compressed textures. The fork already has optional parallel CPU uploads. Its CPU texture-upload instrumentation showed 0.991 ms per frame in the build 10014 slowdown window at frame 26700. The highest reported non-startup window averages were 2.718 ms per frame for 10014, 1.611 ms for the long 10017 run, and 2.339 ms for fresh 10017. Individual spikes could be larger. Account for those spikes and GPU headroom before trading the CPU path for another GPU workload. [Eden upload paths](https://git.eden-emu.dev/eden-emu/eden/src/commit/d85bad89248fcae68f812d7e1c937436261404cb/src/video_core/texture_cache/texture_cache.h#L1165-L1207), [Fork upload path](../games/totk/android/gfx/vk_res.c)

Use matched saves, driver, rendering settings, display mode, build and starting thermal conditions for each comparison. Compare fresh and aged runs separately. Record time to LMKD exit and whether the full aged route finishes across repeats. A clean short warp establishes that the destination loads in that process state. It cannot establish that the aged route survives.

## Application to this fork

The S23+ trials found very few idle shared-image bytes near the foreground kill, with most block slack spread over
partially occupied allocations. Densest-block placement failed to control the high-water mark after the round trip.
The follow-up build tested smaller blocks and also failed during the return warp. The low-memory default stays at
32 MiB, with 16 MiB and denser placement independently selectable for experiments. The allocator now schedules
full shared-image scans only at the next possible expiry and keeps the image-lifetime and fence rules.
Build 10021 skipped 99.1% of these traversals. Pipeline collection now selects the slowest observed
capture builds and measures actual first demand for the selected keys. The eight-key test warmed successfully but
the keys did not recur in the subsequent route. A scheduler trace documented runnable time in the recorder workers.
